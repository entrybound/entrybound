## 2. Question

How well do CDC constructions and size classes:

- preserve chunk boundaries;
- limit new unique stored bytes (update locality);
- resynchronize after an edit?

Each is asked under:

- synthetic edits: inserts, deletes and overwrites of 1 B to 1 MiB; bursts; block moves; prepend and append;
- real consecutive versions (F17 two-version kernel trees, F18 release and snapshot series);
- adversarial periodic or low-entropy content (F20 `gear-extremes`, F15, F16).

## 3. Hypotheses

- **H1a (locality bound).** For every CDC candidate and every edit ≤ 4096 B, the item-level p95 of `new_unique_bytes` is ≤ 3 × the configured maximum chunk size on every non-F20 item. `fixed-size` violates this for insert and delete. **Falsified if** any non-F20 item exceeds it for a CDC candidate (that candidate is then recorded with a locality defect for review, not eliminated: the metric is secondary).
- **H1b (resynchronization).** `gear-spread-nc2` and `fastcdc-2016-nc2` have p95 `resync_distance_bytes` no larger than `gear-norm-v1` at matched realized means, on at least 80% of items. **Falsified if** it is below 80%.
- **H1c (real versions).** At matched realized means, no construction's F18 group-mean log ratio of pair `dedup_stored_fraction` (vs `gear-norm-v1`) lies beyond the T-01 band. **Falsified if** any family-level group mean does.
- **H1d (adversarial).** On F20 `gear-extremes`, at least one of AE, RAM, SeqCDC or `gear-norm-v1` degenerates: `forced_max_fraction` ≥ 0.5 (read from EXP-CHUNK-002) and `insert_64_new_unique_bytes_p95` ≥ 2 × the maximum chunk size.
- **H0.** No construction differs from `gear-norm-v1` beyond the T-01 band on any family, and synthetic-edit metrics are ordered identically for all CDC candidates.
- **Controls (binary; run invalid on failure):**
  - `local_rechunk_mismatches` = 0 (the local re-chunking optimization must match full re-chunking of a 32 MiB prefix on 10 sampled edits per item, in addition to the unit tests);
  - the `fixed-size` negative control of EXP-CHUNK-001.

## 10. Metrics

| Metric | Canonical | Role | Unit |
|---|---|---|---|
| `dedup_stored_fraction` (version-pair arm: unique chunk bytes over v1 ∪ v2 / logical bytes of both) | yes (M05.4) | diagnostic (chunker component) | ratio |
| `{kind}_{size}_preserved_boundary_fraction_median` | no | secondary | fraction |
| `{kind}_{size}_new_unique_bytes_p95`, `burst_*`, `move_*`, `prepend_*`, `append_*`, `version_new_unique_bytes` | no | secondary (update locality; no canonical band exists, §0.2 item 4) | B |
| `{kind}_{size}_resync_distance_bytes_p95` | no | secondary: bytes from the edit end to the first boundary shared with the original (shift-adjusted) | B |
| `local_rechunk_mismatches` | no | tool-validity binary | count |
| `result_sha256`, `detail_sha256`, `algorithm_id` | no | repeat-hash and provenance | string |

Update locality has no banded canonical metric. It can eliminate or select only through `artifact_bytes` of multi-version archives (EXP-CHUNK-004). This gap is recorded for the design review.

## 11. Replication

2 repetitions and repeat-hash (§4.6, §4.13). Seeds are fixed, so values are exact. No adaptive rule.

## 12. Analysis

- **L1:** per (item, cell), the median and p95 over seeds. Matched realized means use `mean_chunk_bytes` from EXP-CHUNK-002 Stage A for the same item and candidate, with the log-log interpolation of EXP-CHUNK-001 section 12.
- **L2-L4:** group and family means of log ratios versus `gear-norm-v1` (secondary metrics: log ratio with +1 B smoothing for byte counts that can be 0; fractions compared as differences), equal family weights, labelled `UNADJUSTED`, `PRE_FREEZE`.
- **Locality-bound check (H1a):** a per-candidate, per-item pass/fail table.
- **Normalized edit amplification:** `new_unique_bytes / max(edit_bytes, 1)` per cell, and its scaling with target size (Stage B), fitted as a log-log slope per construction. This is descriptive.
- **Combined tuning screen.** A candidate with an H1a locality defect on ≥ 2 non-F20 families is flagged. EXP-CHUNK-004's survivor list is EXP-CHUNK-002's survivors minus flagged candidates, unless the flagged candidate is `gear-norm-v1`, which is always kept (and the defect recorded as counterevidence).

## 13. Thresholds

T-01 (`metric_thresholds.dedup_stored_fraction`) for the version-pair arm only. No bands exist for the secondary metrics, so no verdicts are made on them.

## 14. Sensitivity

- Edit size strata are never pooled.
- Truncation prefix 256 MiB versus 64 MiB (a rerun on a 10-item subsample).
- Largest file versus second-largest file (a rerun on a 10-item subsample).
- Pairing rule variant: pair each version with the first version instead of the previous one.
- With and without F20.

## 15. Expected negative results

- All CDC candidates are indistinguishable on real version pairs, so locality does not discriminate algorithms, only sizes.
- Block moves defeat none of them.
- Prepend defeats `fixed-size` only.
- AE's lower size variance does not improve locality.

## 16. Threats to validity

- Synthetic edit distributions (uniform offsets) are not realistic editing patterns; real versions are the external anchor.
- Pairing by path misses renames. The rename/move effect is covered by the move arm and by EXP-CHUNK-007.
- The 256 MiB truncation and the single-largest-file rule hide behaviour on the largest files and on secondary files of an item.
- The local re-chunking optimization could be wrong; mitigated by the binary check.
- Version series in F18 share upstream projects with F01/F02 items (a covariate; reported).

## 18. Tooling to build

1. **`ebr-chunk edit-sweep`** (`research/harness/crates/ebr-chunk/src/edit_sweep.rs`), extending `shift_stability.rs`.
   - **Inputs:** multi-size, multi-seed edit cells; bursts, moves, prepend and append; `--files largest:N:min-bytes:B`; `--prefix-bytes`.
   - **Local re-chunking:** re-chunks from the last original boundary at least one maximum chunk before the edit, and stops at the first resynchronized boundary. Per algorithm, valid only where state resets at chunk boundaries. Each algorithm declares this; algorithms that do not reset use full re-chunking. A unit test plus the runtime `--verify-local-rechunk N` sampling (edits placed in the first 16 MiB, full re-chunk of a 32 MiB prefix) prove equality with full re-chunking.
   - **Metrics:** new unique bytes are computed against the original file's chunk-digest set. The `--version-pairs <manifest>` arm computes pair unique bytes and `dedup_stored_fraction`.
   - **Output:** summary cells as named in the spec keys (`payload.cells.<kind>_<size>.*`, `payload.versions.*`); `result_sha256` over canonical cell JSON; detail JSONL per edit.
2. **`research/experiments/EXP-CHUNK-003/make_pairing.py`** and committed `pairing/*.json`.
3. **`analyze_edits.py`.**

Note for tooling: the ebr runner's `stdout_json` key path is dotted and has no list indexing (`research/tools/ebr/run.py` `_json_key`). The example `payload.edits[0].…` in `ebr-chunk/README.md` does not resolve. Summary cells must therefore be objects keyed by name.
