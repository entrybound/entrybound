# EXP-ECO-016: Default-safety census (`unsafe_defaults`) of the CLI against incumbent extractors and crypto tools

| Field | Value |
|---|---|

## 1. Question

With no flags beyond those needed to perform the task, which dangerous restorations, trust decisions, overwrites and confidentiality downgrades does the implemented CLI perform by default, and how does that compare with incumbent tools' defaults on the same pre-registered scenarios (GNU tar, bsdtar, Python `tarfile` filters, Info-ZIP, 7-Zip, node-tar, .NET, PowerShell `Expand-Archive`, age, gpg, minisign, OpenSSH signing)?

## 2. Hypotheses and falsification

- **H1 (status-quo unsafe defaults).** The status quo has `unsafe_defaults` > 0 on the scenario list; expected members: setuid/setgid restored by default when extracting as root (DEC-PLT-043), a detached signature by an arbitrary key satisfying the require-signature check (DEC-CRY-082), exit status 0 for keyless verification of an encrypted archive whose private content is unverified (DEC-INT-021). *Falsified* if the count is 0.
- **H2 (incumbent parity).** Python `tarfile` with its `data` filter has an `unsafe_defaults` count no greater than the status quo on the extraction scenarios. *Falsified* if Python's count is greater.
- **H3 (no silent overwrite).** The status quo never overwrites an existing destination object by default (DEC-INT-004 status quo). *Falsified* by any overwrite.

## 3. Decisions informed

DEC-PLT-007, DEC-PLT-043, DEC-PLT-001, DEC-PLT-009, DEC-PLT-012 (incumbent overwrite-policy survey), DEC-INT-004, DEC-CRY-082 (attack test), DEC-CRY-061, DEC-CRY-019, DEC-CRY-058, DEC-INT-021, DEC-ECO-023 (which concepts are safe to hide behind defaults).

## 4. Candidates

- Status quo: dev-HEAD `ebound` (and REF-PROD `9e44608`).
- Ledger candidates are **not** implemented here; for each decision the census establishes which scenarios each candidate's stated default would change (a mapping `candidate-defaults.yaml`, transcribed from the ledger descriptions and reviewed by the candidate owner before any run). Examples: DEC-PLT-043 `strip-special-bits-allow-flag` flips DS01 to safe; DEC-CRY-082 `allowed-public-keys` flips DS20; DEC-INT-021 `distinct-exit-code` flips DS22.
- Incumbents (pinned): GNU tar 1.35 (root and unprivileged); bsdtar 3.7.2; Python 3.12 `tarfile` with `filter='data'`, `'tar'`, `'fully_trusted'`, and Python 3.14 default; Info-ZIP `unzip` 6.0; 7-Zip 23.01; node-tar (npm `tar`, pinned) default `x`; .NET `System.Formats.Tar.TarFile.ExtractToDirectory` and `ZipFile.ExtractToDirectory` (pinned SDK, WSL); PowerShell `Expand-Archive` and Windows `tar.exe` (Windows host); age 1.x, gpg 2.4, minisign, `ssh-keygen -Y verify`, cosign `verify-blob` for the trust scenarios.

## 6. Environment and platform requirements

WSL2 Ubuntu 24.04: root and `setpriv --reuid=65534 --regid=65534 --clear-groups` (no account creation); ext4 scratch under `/root/eb-research`; each extraction inside a fresh per-sample directory whose parent contains canary files for DS05-DS09 detection. Windows host (non-admin) for DS17-DS18 and Windows extractors. Downloads for pinned incumbents. No network otherwise.

## 7. Procedure and commands

Scripts in `research/tools/ecosystem/safety/` (to be written): `fixtures.py` (tar, zip and `.eb` versions of each extraction scenario, built with format-building code rather than filesystem capture where the filesystem cannot hold the entry, per F-18); `run_tool.py --tool <t> --scenario <DSxx> --as root|nobody --scratch <dir>` (runs the minimal default command for the task, recorded in `commands/<tool>.yaml`); `oracle.py` (inspects the destination and canaries: modes via `stat`, device nodes, capabilities via `getcap`, xattrs via `getfattr`, ACLs via `getfacl`, links via `readlink`, files outside the destination, overwrite by content hash, exit status, stderr); `ebr run --spec spec.yaml`; `census.py` computes per-tool `unsafe_defaults` and per-candidate flips from `candidate-defaults.yaml`.

## 8. Seeds, warmup, replication

Seed 2026091716 for fixtures and order. 2 repetitions per (tool, scenario, user) in different processes; outcome must be identical (else reported nondeterministic). No warmups.

## 10. Normalization and aggregation

AGG-W (sum of unsafe defaults over scenarios) per tool and user; per scenario table across tools.

## 11. Statistical analysis and use in the decision rule

Deterministic binary facts. `unsafe_defaults` > 0 is an HC-05 violation for the status quo (a defect under objective §2.0 rule 5) and eliminates at R1 any candidate whose stated default reproduces it. Incumbent counts are reported as capability-matched comparisons (§10.1 item 2). Candidate flips are design facts pending the candidates' implementations, which must be re-measured by this same census before any validation look.

## 12. Practical-significance thresholds

Binary metrics per §3.3; T-20 for actionability.

## 13. Sensitivity analysis

Root versus unprivileged user; ext4 versus XFS scratch (read-only XFS loop image for capability and ACL restoration semantics); Python 3.12 versus 3.14 defaults.

## 14. Held-out (Phase D placeholder)

Conventions §5: a sealed scenario variant list (same classes, different construction details) opened after the freeze and run once on every candidate CLI that reached the freeze.

## 15. Expected negative results worth recording

Incumbents with more unsafe defaults than the status quo (GNU tar as root restoring ownership and special bits), and the status quo having unsafe defaults in signature and verification semantics rather than extraction.

## 16. Threats to validity

The "minimal default command" per tool is a judgment (reviewed against each tool's manual); running as `nobody` differs from a normal user with a home directory; WSL2 kernel capabilities and LSMs differ from typical distributions.

## 17. Cost estimate

About 4 h compute; about 5 GB disk (the 1 GiB bomb is generated once and streamed); agent effort scripted plus judgment for `commands/*.yaml` and `candidate-defaults.yaml` (candidate-owner review).
