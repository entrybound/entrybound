# Baselines: incumbent configs, capability matrix, size/determinism pass

This directory is the incumbent-baseline tooling for the Comprehensive
Entrybound Evidence and Product-Decision Research Program (see
`research/PROGRESS.md`, Phase B1). It answers three questions with real,
reproducible measurements, timing disabled throughout (per the program's
quiet-machine constraint):

1. **What exactly are the incumbents, pinned to exact versions?**
   `configs.json` (config definitions) + `tool-versions.json` (probed exact
   versions, generated by `probe_tool_versions.py`).
2. **How big are their outputs, are they deterministic, and do they round-trip?**
   `run_baselines.py` drives the `research/tools/ebr` runner over
   `research/corpus/manifest.json` (tuning+validation splits) and writes
   hash-chained raw rows to `research/raw/EXP-BASE-SIZE/` and normalized CSVs to
   `research/normalized/EXP-BASE-SIZE/`.
3. **What do they preserve, and what can Entrybound not yet be excused from?**
   `capability-matrix.csv` (generated by `build_capability_matrix.py` from
   `probes/run_capability_probes.py`'s results), covering every incumbent
   family's representative config **and Entrybound itself** (`ebound`, built
   from a clone of this repo's own `dev` HEAD).

## Configs (`configs.json`)

Pinned incumbent configurations, one JSON object per config with an exact
`create`/`extract` command template, `params`, and a stated
`determinism_expectation` (what the config's own design implies, not what was
measured -- the measured verdict lives in the normalized CSV / capability
matrix). Families covered: ZIP/DEFLATE (Info-ZIP `zip -6/-9`, `7z -tzip -mx=9`),
tar+gzip (gzip `-6/-9`, pigz single- vs multi-thread), tar+zstd (`-3`, `-19`,
`--ultra -22 --long=27`, `-T1` vs `-T0`), tar+xz (`-6`, `-9e`, pixz indexed),
tar+lz4, tar+brotli `-q11`, 7z/LZMA2 (`-mx=5`/`-mx=9`, solid and `-ms=off`),
squashfs (zstd/xz), WIM (LZX, LZMS-solid), borgbackup and restic (dedup
repositories), DwarFS (official static `dwarfs-universal` release binary,
v0.15.7), and zpaq (upper-bound incumbent). `configs.json`'s `not_run_this_pass`
records `zstd --patch-from` (versioned-tree delta): its base+target shape does
not fit the single-item loop below, so it needs its own script -- not yet
written this pass (see Open items).

## Size/determinism pass (`run_baselines.py`, `EXP-BASE-SIZE`)

`run_baselines.py` builds a single `ebr.spec.v1` spec (one candidate per
config, `configs.json`'s commands turned into real shell) and drives it through
`python -m ebr {validate,run,verify-raw,normalize}`. Every sample:

- creates the artifact at a fixed scratch name (`artifact.bin`, or a directory
  for the two dedup-repo configs) and prints one JSON stdout line
  (`probes/finalize_artifact.py`) giving `artifact_bytes`, `artifact_sha256`
  (files only) and `artifact_tree_sha256`/`artifact_logical_tree_sha256` (both
  work uniformly for a file or a repository directory, reusing
  `research/corpus/tools/fingerprint.py`'s own definitions -- the same ones
  `research/corpus/manifest.json`'s pins use);
- is repeated (`repetitions: 2`), so ebr's normalizer groups
  `artifact_tree_sha256` per (candidate, item) and a non-singleton set of
  digests **is** the determinism verdict -- no separate "is it deterministic"
  step;
- is round-trip-verified by `probes/roundtrip_check.py`, which extracts with
  that config's own incumbent tool, fingerprints both the source item and the
  extraction with `fingerprint_path` (content_tree_sha256 / logical_tree_sha256,
  the same "logical tree fingerprint" language `research/PROGRESS.md` uses
  elsewhere), and gates the `roundtrip_ok` metric on **content** equality only
  (the portable, format-agnostic bar). `logical_tree_sha256` equality (full
  metadata: mode/owner/xattrs/data-extents) is recorded for every sample in
  `research/raw/EXP-BASE-SIZE/roundtrip-detail.jsonl` but does not gate
  validity, because several legitimate incumbents (WIM, squashfs's own
  permission normalization, ...) are not expected to reproduce every field that
  hash checks, and ebr's spec schema has no notion of a non-gating check metric.
  On a content mismatch, `roundtrip-detail.jsonl` also records a plain
  path-level diff (added/removed/changed relative paths) -- "exactly what
  differed."
- Single-member extraction is a per-config property, not a per-item metric:
  `configs.json`'s families note the tool used and whether it needs to decode
  the whole stream first (e.g. `tar+gzip` cannot avoid it; `squashfs`, `wim`,
  `dwarfs`, `borg`, `restic` can address one member directly; `7z`/`zip`
  central-directory formats can). The same evidence appears as the
  `partial_retrieval`/`random_access` rows of `capability-matrix.csv`, each
  probed or cited per config there rather than duplicated here.

Reproduce (inside WSL Ubuntu; `disk_guard.py` must pass first):

```sh
wsl.exe -d Ubuntu -- bash -lc '
  cd /mnt/d/Projects/entrybound/entrybound
  export PYTHONPATH=research/tools
  export PATH=/root/eb-research/tools/dwarfs:$PATH
  PY=/root/eb-research/venv/bin/python
  $PY research/baselines/run_baselines.py spec \
    --scales small,medium,large --splits tuning,validation \
    --repetitions 2 --timeout-s 1800 \
    --out research/baselines/specs/EXP-BASE-SIZE.yaml
  $PY research/baselines/run_baselines.py run --spec research/baselines/specs/EXP-BASE-SIZE.yaml
'
```

`f19-tuning-zoo` (the deliberately hostile-filename fixture item) is excluded
from every generated spec (`run_baselines.py`'s `KNOWN_BROKEN_ITEMS`): it
triggers a pre-existing path-corruption bug in `research/tools/ebr/corpus.py`
(`_walk`/`compute_fingerprint` reuse a display-safe backslash-to-slash
replacement as a real filesystem path), unrelated to any baseline config,
flagged as a follow-up rather than fixed here (see Open items).

### Status of this pass at the last checkpoint in this session

`EXP-BASE-SIZE-small` (28 configs x the 40 non-excluded small-scale
tuning+validation items x 2 repetitions = 2,240 samples) ran for one session
and was stopped cleanly (`ebr run` killed between samples, not mid-sample) at
**140/2,240 rows** (run `20260917T031201Z-e86b28`; 139 valid, 1 correctly
invalid: `zpaq-m5` on an item containing a symlink, the documented zpaq
limitation above). It is **far slower per sample than expected** (multiple
seconds each, dominated by the slower configs -- `7z -mx9` x3, `xz -9e`,
`brotli -q11`, `zstd --ultra -22`, plus process-spawn/repo-init overhead for
borg/restic/dwarfs -- even on small inputs), so a single session cannot
complete the full small-tier matrix, let alone medium/large. Because
`order: randomized_blocks` runs every candidate x item once before starting a
second repetition, **all 140 rows so far are repetition 0**: zero
(candidate, item) pairs have 2 repetitions yet, so `capability-matrix.csv`'s
`deterministic_output` rows honestly read `N/A` ("not yet enough
repetitions"), not a guessed `YES`/`NO` -- `build_capability_matrix.py`
counts actual raw-row repetitions per pair rather than trusting `ebr`
normalize's deduplicated-digest-set view, which would otherwise misread "only
one observation so far" as "confirmed deterministic." Bytes and `roundtrip_ok`
*are* real, verified data for all 140 rows.

Medium- and large-scale coverage (`--scales medium`, `--scales large
--large-items ...`) has not been attempted this pass; `run_baselines.py spec
--medium-sample N` supports a deterministic evenly-spaced subset for a future,
time-boxed continuation instead of all 77 medium items. To resume: rerun the
reproduction command above (same spec, same experiment_id) with a fresh
`--run-id`; `ebr normalize --include-incomplete` (needed while any run's
status is `running`, e.g. after another mid-session stop) folds every run's
rows together automatically.

## Capability probes (`probes/`, `capability-matrix.csv`)

`probes/make_fixtures.py` builds a fixture tree covering every PROBE-able
capability: Unicode and non-UTF-8 filenames, a fixed mtime/atime, a
permission range (0600/0644/0700/0755), non-root ownership (uid/gid 1000),
relative/absolute/dangling symlinks, a hardlink pair, a POSIX ACL
(`setfacl`), an xattr (`setfattr`), and a sparse file (`fallocate
--dig-holes`). `probes/run_capability_probes.py` creates+extracts it through
one representative config per incumbent family plus Entrybound, and diffs the
result against the fixture; `build_capability_matrix.py` turns that JSON plus
a set of DOC-cited rows (encryption, authentication, random access, streaming
-- properties the fixture round-trip can't exercise, or that would need a
second, encrypted/authenticated run to probe directly) into
`capability-matrix.csv` (`system_config, capability, support, method,
evidence_ref, notes`). `deterministic_output` rows are **not** re-probed here:
they are read back from the real `EXP-BASE-SIZE` size pass above (or, for
Entrybound, a direct two-run `ebound pack` hash comparison), so the matrix
never states a determinism verdict that disagrees with the measured one.

ctime is recorded as `N/A` for every config: it is the inode's own
last-metadata-change time, always set by the extraction operation itself, so
no archive format or tool can "preserve" it -- there is nothing to compare.
Birth/creation time (`stat -c %W`) is recorded as probed but `N/A`/`NO`
throughout: ext4 exposes a crtime, but none of the probed tools attempt to set
one on extraction, and GNU coreutils' own birth-time read support is
inconsistent across kernels.

Reproduce:

```sh

  /root/eb-research/venv/bin/python research/baselines/build_capability_matrix.py
'
```

### Findings worth carrying into Phase C (all PROBE, not asserted from memory)

- **zpaq drops symlinks silently on `add`**, not merely on extract (7.15, this
  build): a symlink in the source tree is simply absent from the archive, with
  no error. Any corpus item containing a symlink (most real source trees)
  will legitimately fail `roundtrip_ok` for `zpaq-m5` in the size pass -- that
  is a correct, expected result, not a harness bug.
- **7z (`-snl`) and Entrybound's tar-export path both refuse an absolute-path
  symlink** at extract/export time ("Dangerous link path was ignored" /
  `EB_LEGACY_EXPORT_REFUSED ... no native symlink representation"), though for
  different reasons: 7z treats a symlink whose resolved target lands outside
  the extraction root as a security hazard and skips just that entry
  (continuing with everything else); Entrybound's tar export in this dev-HEAD
  build refuses the **whole conversion** transactionally for **any** symlink
  entry (not only absolute ones -- see `capability-probe-results.json`'s
  `entrybound-ebound.strict_refusal_findings.symlink_export`), which is a
  narrower symlink-export gap than 7z's, not merely a stricter security
  posture. Info-ZIP `zip -y` and 7z (both fixed to store, not follow, symlinks)
  need this flag explicitly -- its absence was the very first bug this pass
  found (`zip` and `7z` without `-y`/`-snl` silently **dereference** symlinks
  into regular files/directories, corrupting the round trip; see the
  `run_baselines.py` git history in this checkpoint).
- **Entrybound's `ebound pack` refuses non-UTF-8 filenames outright**
  (`EB_EAM_INVALID_PATH_COMPONENT`) and **refuses a tree whose POSIX ACL mask
  disagrees with its reported mode bits** (`EB_EAM_INVALID_ACL`) -- both are
  whole-tree refusals in this dev-HEAD build, unlike every incumbent probed
  here (which either preserve or silently drop these cases). Whether these are
  intentional strictness (an explicit design decision, not yet documented in
  a committed decision) or missing-capability gaps in the experimental
  bootstrap CLI is a question for the program owner / a Decision Ledger entry,
  not resolved by this probe.
- **This dev-HEAD `ebound` CLI has no direct "extract archive to a directory"
  command**: retrieving files today means `ebound convert <archive.eb>
  <out.tar> --to tar` (or `ebound publish ... --target tar`) followed by
  extracting that tar. `partial_retrieval` is therefore recorded as `PARTIAL`
  for Entrybound, not because the format can't support it (`--layout indexed`
  is explicitly the random-access organization per the CLI's own `--help`
  text) but because no subcommand exposes it yet.
- Non-UTF-8 and non-conforming-ACL filenames are exactly the fixtures that hit
  the pre-existing `ebr`/`corpus.py` bug noted above; this pass worked around
  it in its own probe scripts (`errors="replace"` on subprocess decoding, a
  bytes-safe `os.listdir` where needed) rather than depending on the shared
  `ebr.corpus` fingerprinting path for the capability probes.

## Fair-comparison rules for capability-matching (read before citing this matrix in a domain report)

1. **A baseline's stated limitation is never grounds to exclude the
   corresponding cost from Entrybound.** If zpaq can't carry symlinks, that
   does not mean symlink-carrying corpus items should be dropped when
   comparing Entrybound to zpaq -- it means zpaq's ratio numbers on those
   items are for a **smaller, easier problem** (no symlinks to represent) than
   Entrybound is solving, and any ratio comparison must say so.
2. **`support: NO` or `PARTIAL` is reported, not silently substituted.** Where
   a config lacks a capability another needs for a fair fight (e.g. zip's
   default weak-crypto-only encryption vs Entrybound's AEAD), the matrix
   states the gap (`method: DOC`, cited) rather than picking a "closest
   equivalent" flag that changes what is actually being measured.
3. **`method: PROBE` outranks `method: DOC`** whenever both exist for the same
   (config, capability) pair: a citation describes intended behavior, a probe
   describes what this exact pinned version actually did in this environment.
   Where this pass has only `DOC` (encryption, authentication, streaming,
   random access for most configs -- exercising these needs either a second,
   differently-configured run per config, e.g. with `--recipient`/`--password`
   set, or purpose-built streaming/seeking test harnesses, neither built this
   pass), that is stated in the row's own `notes`, not hidden.
4. **`N/A` means "not a meaningful comparison for this pair"** (ctime; a
   dedup-repo's directory-level determinism once encryption/snapshot metadata
   is unavoidably random), never "no data yet" -- rows that are simply
   unmeasured say so explicitly instead (e.g. the `deterministic_output`
   placeholder rows this script writes if `EXP-BASE-SIZE`'s `summary.json`
   does not exist yet).
5. **Solid/non-solid, single- vs multi-thread, and indexed vs plain variants
   are separate configs**, not a single row per tool: `7z-mx9-solid` and
   `7z-mx9-nosolid` trade ratio for random access explicitly (REQ-CMP-0160);
   collapsing them would hide exactly the trade a fair report needs to state.
